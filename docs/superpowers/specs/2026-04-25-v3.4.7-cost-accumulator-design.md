# v3.4.7 — Lifetime Cost Accumulator

_Brainstormed: 2026-04-25 — successor to v3.4.6 (C2+C3+C4)_

## Goal

Show **lifetime cost since hatch** on `purrgotchi stats` — a single dollar number that grows whenever Claude Code is used while Thalia is around. The `state.lifetime_cost_usd` field has existed since Phase 1 but has never been written; this patch wires it up.

## Why now

Originally scoped into v3.4.6 but deferred to keep that bundle focused. The stats card's `Progress` section currently shows tool calls and coins; cost was the third progress metric expected by the design. Without it, `state.lifetime_cost_usd` is dead data.

## Non-goals

- Per-session cost breakdown or history
- Burn-rate / cost-per-day metrics
- Threshold decorations ("Thalia has cost you $100!")
- Changes to the HUD's existing per-session `Total: $X.XX` line
- Retroactive baseline from prior sessions (zero baseline accepted; see §3)

## 1. Where the accumulator lives

**Decision: in `statusline::run`, not `feed_inner`.**

Hook wiring inspection confirmed that `statusline` is the only entry point that ever receives `payload.cost.total_cost_usd`:

| Entry point | Hook event | Receives `total_cost_usd`? |
|---|---|---|
| `purrgotchi feed`       | PostToolUse       | ❌ no |
| `purrgotchi turn`       | UserPromptSubmit  | ❌ no |
| `purrgotchi statusline` | statusLine        | ✅ yes |

The master-plan note's mention of `feed_inner` was based on a misreading; the implementation must live in `statusline`.

## 2. Algorithm — monotonic delta per `session_id`

The Claude Code statusline payload includes a `session_id` (UUID, one per Claude Code invocation). Using it as the accumulation key handles parallel sessions correctly: two CC windows in two projects each track their own cost independently with no cross-contamination.

### Sidecar file

Path: `<cache_dir>/cost_sessions.json` (use existing `paths::` helper for cache dir).

Format:
```json
{
  "2de8ac34-3a21-4816-9b82-824f39c5bb99": { "last_cost": 59.32436785, "last_seen_ts": 1714060800 },
  "<other-uuid>": { "last_cost": 0.42, "last_seen_ts": 1714050000 }
}
```

The sidecar lives in the cache tier — it is loseable. Worst case of corruption/loss: we lose at most one render's worth of accumulated delta per active session. State.json (the precious tier) is the source of truth for `lifetime_cost_usd`.

### Per-render flow

On each `statusline::run`:

1. Parse `session_id` and `cur = payload.cost.total_cost_usd` from the input JSON.
2. **Skip the accumulator** if `session_id` is empty/missing (don't create a phantom `""` entry collecting unattributed cost).
3. Load sidecar (default to empty map on missing/corrupt file).
4. `prev = sidecar[session_id].last_cost` (default `0.0` if `session_id` not yet known).
5. `delta = max(0.0, cur - prev)`. The `max(0.0, …)` guards against any CC payload weirdness where reported cost briefly drops.
6. **If `delta > 0`:** load state, `state.lifetime_cost_usd += delta`, save state atomically.
7. Update sidecar entry: `session_id → { last_cost: cur, last_seen_ts: now }`.
8. **Lazy GC:** while we have the sidecar loaded, drop any entry with `last_seen_ts < now - 30 days`.
9. Save sidecar (best-effort write; failure here is logged at debug only — not fatal).

### Write-order rationale

**Order: sidecar save → state save.** The sidecar is the "I have already credited this cost" bookkeeping; it must advance _before_ the corresponding lifetime increment is committed.

Failure modes under this ordering:

- **Sidecar save fails (state never attempted):** sidecar untouched, state untouched. Next render sees the same `prev` and recomputes the same `delta`. Retried automatically. No loss, no duplication.
- **Sidecar save succeeds, state save fails:** sidecar advanced to `cur`, but `lifetime_cost_usd` not persisted. Next render sees `prev = cur`, computes `delta = 0`. The increment that just failed is **lost** — but exactly once, never duplicated.

The opposite ordering (state-first) would risk double-counting: if state commits but sidecar fails, the next render would treat the already-credited delta as fresh and add it again. For a vanity metric, **lose-at-most-once-per-failure** beats **potentially-double-count**, so sidecar-first wins.

### Why no high-water-mark / "session boundary" logic

An earlier sketch used a single high-water-mark with `cur < high_water` as the session-boundary trigger. Rejected because:

- Multiple CC windows running in parallel break it: session B's `total_cost_usd = 0` looks like a boundary in session A's log.
- The `session_id`-keyed delta approach handles parallelism naturally.
- It's also simpler — no boundary detection needed at all.

## 3. Baseline

**Zero baseline.** When v3.4.7 ships, `state.lifetime_cost_usd` stays at its current `0.0` value for everyone. No retroactive estimation from `total_tool_calls` or other proxies.

The card will read `Cost: $0.00` immediately after install and grow from there. The gap closes naturally over a few days of use.

## 4. Display — stats card

Add one row to the **Progress** section, immediately after `Coins:`:

```
Cost: $59.32
```

- Color: `C_YELLOW` (matches `Coins:` and other money-flavored fields).
- Format: `${value:.2}` — two decimal places, plain dollars.
- Source: reads `state.lifetime_cost_usd` directly from disk at command time.
- No live addition of "current session high-water from sidecar" — keeps the stats output deterministic and avoids `stats` needing to touch the sidecar. The user accepts that the lag between a render and the next render's accumulation is small (cents at most).

The HUD's existing per-session `Total: $X.XX` line is **untouched**.

## 5. State schema

No schema bump. `lifetime_cost_usd` already exists with `serde(default)` semantics; we are merely starting to write to it. Existing v3.4.6 state.json files load and accumulate without migration.

## 6. Edge cases

| Case | Handling |
|---|---|
| Empty/missing `session_id` in payload | Skip accumulator (no sidecar update, no state write). |
| Sidecar file missing | Treat as empty map; first render of each session contributes its full `cur` as delta (or zero if it's still at zero). |
| Sidecar JSON corrupt | Treat as empty map; log at debug; first render rebuilds it. Worst-case loss: one delta per session that was active at the time of corruption. |
| Cur drops below prev within a session | `delta = max(0.0, …)` clamps to zero. Sidecar still advances to new `cur` so we don't double-credit if cur recovers. |
| Sidecar fills with stale entries | Lazy 30-day GC on each render keeps it small. With typical usage (a handful of sessions per day), the file should rarely exceed a few KB. |
| Sidecar write fails (state never reached) | Sidecar and state both untouched; next render retries the same delta. |
| State write fails after sidecar succeeded | This delta is lost (sidecar already advanced to `cur`; next render sees `delta = 0`). One-render loss; no double-count. |

## 7. Tests

**Unit tests in a new `cost_acc` module (or extending `cost.rs`):**

- `delta_zero_for_new_session_starting_at_zero` — first render of new id, cur=0 → delta 0, lifetime unchanged.
- `delta_equals_cur_minus_prev_within_session` — same id, cur grows → delta is the difference.
- `delta_clamped_to_zero_when_cur_drops` — same id, cur drops → delta 0, sidecar advances to new cur.
- `parallel_sessions_independent` — two ids interleaved, each accumulates own deltas, no cross-contamination.
- `gc_drops_old_entries` — entries older than 30 days are removed; recent ones retained.
- `empty_session_id_skips_accumulator` — empty string id doesn't create a phantom entry, no state mutation.
- `corrupt_sidecar_recovers_to_empty_map` — bad JSON file → next render starts fresh.

**Stats card test:**
- `stats_card_shows_cost_row_with_dollars_two_decimal` — given `state.lifetime_cost_usd = 59.32`, output contains `Cost: $59.32`.

**Manual smoke test:**
1. Note current `state.lifetime_cost_usd` (should be 0).
2. Use Claude Code for a few minutes (some tool calls, some replies).
3. Run `purr stats` — confirm `Cost:` row present with non-zero value.
4. Inspect `cache/cost_sessions.json` — confirm current session id is present with cost matching the live HUD's `Total:` line.
5. Wait for a fresh session (close + reopen Claude Code), use it briefly, run `purr stats` again — confirm cost has grown by approximately the new session's spend.
