# v4.0.0 Phase 1: Mod Skeleton + Hooks Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `mod/` plugin plus a repo-root marketplace that wires `feed` and `turn` into Claude Code without touching `settings.json`. The mod finds and checks the binary, warns about old classic hooks, and never blocks or slows a tool call or a prompt.

**Architecture:** The mod is a thin TypeScript shell (`register(on, options)`) over the Rust binary's Phase 0 `--json` contract. Every binary call goes through one module (`binary.ts`): it resolves the binary, runs it with argv and no shell, parses the JSON, and serialises the calls that change state. Tool calls are counted in memory. A coalescing queue flushes them as `feed --count N` after the hook has returned, with a 2 s clock flush as a safety net. `turn` runs from `classic.UserPromptSubmit` and receives the classic stdin unchanged.

**Tech Stack:** Claude Code 2.1.302 mods API (TS/TSX, `claude-code` + `claude-code/testing`), TypeScript 5.9 for type-checking only, no npm dependencies. The Rust binary is unchanged in this phase.

**Spec:** `docs/superpowers/specs/2026-10-17-v4.0.0-claude-code-mod-design.md` (§3, §3.2, §4.1, §4.7, §4.11, §5 row 1, §6). **Ground truth that OVERRIDES the spec:** `docs/superpowers/plans/2026-10-17-v4.0.0-mods-api-findings.md`. **Binary contract consumed:** `docs/superpowers/plans/2026-10-17-v4.0.0-phase0-json-surface.md` (Tasks 4–8).

This is plan 1 of 5: Phase 1 (this file), then `…-phase2-commands-toasts.md`, `…-phase3-pane-hud.md`, `…-phase3b-pixel-sprites.md` and `…-phase4-polish-release.md`.

## Global Constraints (all mod phases)

- **The d.ts is the authority, not the spec or this plan.** Lay the types once per machine and engine bump with `bash mod/scripts/lay-types.sh` (Task 1.1). Look up any declaration with `grep -n "<name>" mod/.claude-plugin/types/claude-code/index.d.ts`. Never read the whole 651 KB file, never hand-edit it, and never commit `mod/.claude-plugin/types/` (the engine writes a `.gitignore` containing `*` there).
- **Gates for every mod task**, all green before you commit:
  1. `claude plugin validate mod`, plus `claude plugin validate .` whenever `marketplace.json` or `plugin.json` changes.
  2. `npx -y -p typescript@5.9 tsc -p mod`. Validate does NOT type-check: it accepted `$.process.run({ argv })`, which is the wrong shape.
  3. `claude plugin test mod`, with every test passing.
- **No npm dependencies.** Add no `package.json` and no `node_modules`. TypeScript is used only through `npx` for `tsc`.
- **Observer rule.** No game hook may deny, throw past its own try/catch, or make a tool result or a prompt wait on the binary. Every `tool.call` / `classic.*` registration ends with `.catch(($, e, next) => next(e))`. A Purrgotchi failure is invisible to the session apart from at most one toast per session per failure class.
- **`$.process.run(argv, init)` is argv-first**, with `init = { stdin?, timeoutMs?, cwd?, env? }`. It **rejects** on timeout or on a failure to start, and resolves with a non-zero `exitCode` otherwise. Every call passes an explicit `timeoutMs` (constants in `binary.ts`). Every call goes through `binary.ts`; no other file calls `$.process.run`.
- **Argv is fixed.** User or model text reaches argv only as a separate element, and only in `/purr-rename` (≤ 32 chars, Phase 2) and `quip-store` (≤ 500 chars, Phase 4). There is never a shell.
- **The mod never owns durable state.** `$.state` atoms hold view state only, every key is declared in `mod/types/index.d.ts`, and render hooks only `read` (never `update`). Plain module-level variables inside `register` are allowed for transient counters, such as the pending feed count, and die on reload. That is acceptable.
- **JSON consumption rules** (from Phase 0): exactly one line per call. Accept only objects with `v === 1`, and ignore unknown keys. `ok: false` objects are either `ErrorJson` (`error` code) or `ActionJson` (`result: "error"`). The known error codes are `no_kitten`, `state_unavailable`, `bad_input`, `empty_quip` and `write_failed`. Any other code is handled as a generic failure.
- **Tests never run the real binary.** `claude plugin test` mocks `process.run` with Phase 0-shaped fixture JSON from `mod/hooks/testkit.ts`. Op mocks return `{ value }` or `{ deny }`. Engine events return their result directly. Anything the plugin reaches that nothing answers fails with `no implementation for <event>`, so `testkit.engine(on)` answers every op the mod uses. The test's `$` has no `state`, so assert through renders and spies.
- **Dev runs never touch the real kitten.** Live sessions use `bash mod/scripts/dev-sandbox.sh` (Task 1.1). It puts a `purrgotchi` wrapper that exports `PURR_STATE_DIR=<sandbox>` first on `PATH`. Before and after every live run, record `stat -c %Y ~/.claude/purrgotchi/state.json` and confirm it is unchanged.
- **The classic statusline keeps working unchanged.** No mod task edits `rust/`, `install.sh` or the statusline. (Rust tasks in Phases 3/3b/4 say so explicitly and keep the Phase 0 goldens untouched.)
- **Commits** use conventional messages that describe what changed. No `Co-Authored-By` lines. Never stage `docs/superpowers/specs/`. No version bump before Phase 4: the binary stays `3.8.0` and `plugin.json` stays `4.0.0-dev`.

**Deviations from the spec (intentional, so do not "fix" them back):**
- §4.2 / goal 2: commands are **not** namespaced (`register({ name: 'pet' })` is `/pet`), and `/stats` and `/rename` are refused as built-ins. The scheme is **`/purr` plus `/purr-<verb>`** (Phase 2): `/purr`, `/purr-pet`, `/purr-play`, `/purr-treat`, `/purr-card`, `/purr-stats`, `/purr-rename`, `/purr-layout`, `/purr-hatch`. Why:
  - (a) Unnamespaced generic words (`/pet`, `/card`, `/play`) can collide with future built-ins (the d.ts churns by about 30k lines per release) and with other plugins. A prefix is insurance.
  - (b) Typing `/purr` in the typeahead lists every verb with its own description and `argumentHint`, which a `/kitten <sub>` hub would hide behind one entry.
  - (c) `CommandOutput` render hooks match `{ props: { command: 'purr-card' } }` directly, without parsing `args`.
  - (d) It continues the classic `purr <verb>` shell wrapper.
  - **Verified on 2.1.302** (planning probe, `claude -p "/purr" --plugin-dir <probe>`, no model call): all nine names registered and `$.command.list()` listed them with `source: "plugin"`.
- §3.2 "require ≥ 4.0.0": the version is not bumped until Phase 4, so compatibility is a **capability handshake** (`frame --json` answers `v: 1`), not a semver floor. This stays the contract after Phase 4 too.
- §4.1 "`$.process.run` time counts against the hook" is wrong (findings §2). The real cost is that awaiting the feed delays the tool result, so feeds are queued and flushed after the hook returns.
- §4.1 "read `~/.claude/settings.json` via `$.fs`": the mod uses `$.settings.read({ source: 'user' })` instead.
- §4.3 "auto-open where `e.viewport.isFullscreen`": `session.start` has no viewport (Phase 3 handles auto-open).
- §4.7 `userConfig`: every field needs a `title` and a `description`, and `binaryPath` is `type: "file"`. The `theme` boolean is **dropped**, because `themes/` is auto-discovered and a boolean cannot un-ship it; choosing the theme is the user's `/theme` call. The `band` boolean is **dropped**, because §4.10 `layout: "bottom"` supersedes it.
- §4.11 `layout: "off"`: the game hooks are registered **only when `layout !== 'off'`**. That decision is made in `register()` from `options`, because a config change reloads the module. With `off`, the binary is never touched, whatever `restyle` says.

## Review Focus

1. **Parallel tool calls in one turn** (Claude often runs 3–10 tools at once). Every call must be credited exactly once, without spawning N concurrent `feed`s that fight over the 500 ms state lock and drop credits. Pinned in Task 1.4 (`coalesces a burst into one feed --count N`, `requeues on state_unavailable`).
2. **Binary missing, outdated, or hanging.** Tool calls and prompts must behave as if the mod were absent: no exception surfaces, no toast storm (at most one toast per session), and nothing is spawned after a `missing` handshake. Pinned in Task 1.2 (handshake matrix) and Task 1.4/1.5 (`no spawn when status is missing`, `hanging binary never delays the tool result`).
3. **Fresh machine with no `state.json`.** The handshake gets `no_kitten` (exit 1) and must count it as **compatible**, and the first `feed` hatches the kitten as in classic. Pinned in Task 1.2 (`no_kitten is ready`).
4. **Migration double-feed.** If the user still has `purrgotchi feed` in `hooks.PostToolUse` in user settings, they get one toast naming `bash install.sh --uninstall-hooks`. A `statusLine` entry alone must NOT toast. Pinned in Task 1.3 (`scanSettings` table).
5. **Ordering of feed vs turn.** `turn` zeroes `streak_count`, so tool calls credited before a prompt must reach the binary before that prompt's `turn`. Pinned in Task 1.5 (`flushes pending feeds before turn`).

  - `BinaryStatus = { kind: 'unknown' } | { kind: 'ready'; version: string } | { kind: 'missing'; detail: string } | { kind: 'outdated'; version: string }`
- Produces from `binary.ts`:
  - `resolveBinary(o: PurrOptions): string`: the trimmed `o.binaryPath` if non-empty, else `'purrgotchi'`.
  - `TIMEOUT = { feed: 5000, turn: 5000, frame: 3000, command: 5000, quip: 5000, handshake: 3000 } as const`.
  - `RunOutcome<T> = { kind: 'json'; exitCode: number; value: T | ErrorJson } | { kind: 'failed'; reason: 'rejected' | 'not-json' | 'wrong-version'; exitCode?: number; detail: string }`.
  - `runJson<T>($, bin: string, args: readonly string[], init?: { stdin?: string; env?: Record<string, string>; timeoutMs?: number }): Promise<RunOutcome<T>>`. It never throws. A rejection (missing binary, timeout) gives `failed/rejected`. stdout that does not parse as one JSON object gives `failed/not-json` (the first line is used if there are several). An object with `v !== 1` gives `failed/wrong-version`. Otherwise it returns `json`, even when the exit code is non-zero (`no_kitten` exits 1 and still carries JSON).
  - `isError(v): v is ErrorJson`, which is `v.ok === false && typeof v.error === 'string'`.
  - `handshake($, bin): Promise<{ status: BinaryStatus; frame: FrameJson | null }>`. It runs `[bin, 'frame', '--json']` with `TIMEOUT.handshake`:
    - `failed/rejected` gives `missing`.
    - `json` with `ok: true` gives `ready` plus the frame.
    - `json` that `isError` with `error === 'no_kitten'` gives `ready` with `frame: null`.
    - Anything else (`not-json`, `wrong-version`, or another error) gives `outdated`.
    - For `ready` and `outdated` it then runs `[bin, '--version']` and takes `version` from stdout `/^purrgotchi (\S+)/` (or `'unknown'`). `--version` failing never changes the status.
  - `class Serial { run<T>(job: () => Promise<T>): Promise<T> }`: a promise chain. Jobs run one at a time in call order, and a rejected job does not break the chain.
- Produces from `testkit.ts` (test-only):
  - `ok(stdout: string, exitCode = 0)` gives the `{ value: ProcessRunResult }` op answer.
  - `fx` fixture strings, each exactly one JSON line: `fx.feed(patch?)`, `fx.turn(patch?)`, `fx.action(patch?)`, `fx.lines(lines)`, `fx.frame(patch?)`, `fx.error(code, message?)`, and `fx.noKitten = fx.error('no_kitten', 'No kitten hatched yet. Run: purrgotchi hatch')`. Defaults match the Phase 0 tests: frame `name: 'Thalia'`, `breed: 'Maine Coon'`, `rarity: 'rare'`, `level: 12`, `stage: 'young'`, `coins: 340`, `bond: 50`, `mood: 'calm'`, 6 sprite rows, `scene: null`, `celebration: null`.
  - `engine(on, o?: { run?: (argv: string[], init?) => OpAnswer; settings?: object })` answers `session.start`, `command.register`, `ui.toast` / `ui.notify` / `ui.status` / `ui.log` (recording into returned spies `{ toasts: string[]; notifies: string[]; statuses: (string | undefined)[]; runs: string[][] }`), `settings.read` (default `{}`), and `process.run` (routing to `o.run`, defaulting to a handshake answer: `frame` gives `fx.frame()`, `--version` gives `purrgotchi 3.8.0`, everything else gives `fx.feed()`). Phase 2–4 tasks extend `engine` with the ops they add (`ui.open`, `session.model`, `session.usage`, `config.set`, `model.complete`, `process.spawn`). Each one goes in the task that first needs it.

### Task 1.4: Feed: a non-blocking, coalescing `tool.call` observer

**Model:** opus. The concurrency and lifetime reasoning is subtle.

**Files:**
- Create: `mod/hooks/feed.ts`
- Modify: `mod/hooks/runtime.ts` (add `feeds`), `mod/hooks/register.tsx`, `mod/hooks/session.ts` (start the safety clock)
- Test: `mod/hooks/feed.test.ts`

**Design (why this shape):** Awaiting `feed` inside `tool.call` delays the tool result reaching the model by one spawn (findings §2). One fire-and-forget spawn per call races for the 500 ms state lock under parallel tool calls, and `locked_update` drops the credit when the lock is busy (`state.rs` `acquire_lock`). So the hook only increments an in-memory counter after `next(e)` and kicks a flush it does **not** await. A flush runs `feed --json --count N` for everything pending, through `rt.serial`. Calls that arrive during a flush accumulate and go out in the next flush. On `state_unavailable` (lock busy) the count is put back. A `$.clock.every(2000)` started in `session.start` (a long-lived context) also flushes. That covers the case where an unawaited `$` call does not outlive its hook; the planning probe showed a fast unawaited `$.process.run` resolving 16 ms after the hook returned, and Task 1.6 settles it in an interactive session. Neither trigger depends on the other being right.

**Interfaces:**
- Consumes: `Runtime`, `ready`, `runJson`, `TIMEOUT.feed`, `Serial`, `FeedJson`, `isError`.
- Produces: `MAX_FEED_COUNT = 10_000` (it mirrors `cli::MAX_FEED_COUNT`; `--count` above that is exit 2).
- Produces: `class FeedQueue { constructor(onResult: ($, r: FeedJson) => void | Promise<void>); add(n?: number): void; get pending(): number; flush($, rt: Runtime): Promise<void> }`.
  - `add` saturates `pending` at `MAX_FEED_COUNT`.
  - `flush` is a no-op when `pending === 0` or `!ready(rt)`. Otherwise it takes `n = pending`, sets `pending = 0`, and inside `rt.serial.run` calls `runJson<FeedJson>($, rt.bin, ['feed', '--json', '--count', String(n)], { timeoutMs: TIMEOUT.feed })`.
  - `json` with `ok: true` gives `onResult($, value)`.
  - `isError` with `state_unavailable` gives `add(n)` (requeue). `failed/rejected` (timeout) also requeues, but only once per batch: track a `retried` flag so a hanging binary cannot loop forever, and drop the batch on its second failure.
  - Any other failure drops the batch and logs `$.ui.log('feed failed: …', { to: 'debug' })`.
  - The flush itself never throws.
- Produces: `registerFeed(on, rt)`, which registers:
  - `on('tool.call', async ($, e, next) => { const r = await next(e); if (ready(rt)) { rt.feeds.add(1); void rt.feeds.flush($, rt) } return r }).catch(($, e, next) => next(e))`. The tool result is returned without waiting for the flush. Subagent calls (`e.agentId`) count too, as classic `PostToolUse` does.
  - `on('session.end', async ($, e, next) => { await rt.feeds.flush($, rt).catch(() => {}); return next(e) })`. This shares the short `next.budget`, so the flush is bounded by `TIMEOUT.feed`; losing a batch here is acceptable. **Do not** cancel timers on `session.end`: `/clear` fires `session.end` with `reason: 'clear'` and no `session.start` after it.
- `session.ts` `onSessionStart`: when `ready`, start the safety clock **once per runtime**: `rt.flushTimer ??= $.clock.every(2000, () => rt.feeds.flush($, rt))`. Add `flushTimer?: Timer` to `Runtime`. Timers die on hot reload, and the new runtime starts its own.
- Phase 1 `onResult` is a no-op; Phase 2 wires celebrations.
